# Skill：UI 受众与信息边界

## 核心原则

- UI 的受众是产品的实际使用者（下文简称「用户」），而不是开发者 / 测试人员 或 Agent 本身。

默认用户具备理解基础 UI 语言的能力，能够识别标题、按钮、表单、状态、列表、弹窗和常见交互。不要把 UI 设计得像代码注释、开发文档或实现说明。

- 请不要在 UI 上进行过度的解释和说明。

UI 的目标是帮助用户完成任务，而不是向用户证明系统考虑得很全面。

本 Skill 只审查和约束用户可见文案。除非用户明确要求重新设计 UI，否则不要因此新增、删除或修改产品功能、页面结构、布局、组件和交互。

## 默认受众

当前 UI 面向产品的实际使用者，而不是：

* 项目开发者
* 代码维护者
* 架构师
* 测试人员
* Agent 本身
* 提出落盘实现要求的人

不要因为某条信息在开发过程中很重要，就默认认为最终用户也需要看到它

## 信息准入规则

一个信息只有在满足以下条件之一时，才能默认出现在 UI：

1. 用户必须知道它，才能完成当前操作；
2. 用户看到它后，可以采取明确行动；
3. 不展示它会导致高概率误操作、损失或安全风险；
4. 它是当前任务必须反馈的结果或状态。

如果不满足以上条件，默认删除、隐藏或移到二级页面。

## 禁止直接展示的内容

除非产品需求 **明确要求**，否则不要在 UI 中展示：

* 数据库、缓存、文件系统和存储方式
* API、接口路径、请求参数和响应字段
* 内部字段名、枚举值和状态机名称
* 组件名、模块名、服务名和中间件名称
* Cookie、Session、Token 的内部保存机制
* 文件权限、ACL、原子替换等实现细节
* 调试过程、测试过程和开发决策
* 为解释代码实现而产生的说明
* 开发者提供给 Agent 的约束、理由和验收要求

内部信息应进入日志、代码注释、测试、开发文档或维护者文档，而不是用户界面。

## UI 设计规则

### 1. 优先使用 UI 语言

优先通过以下方式表达含义：

* 清晰的标题
* 准确的按钮名称
* 合理的默认值
* 明确的选中状态
* 正确的布局和视觉层级
* 简洁的成功、失败和空状态
* 符合习惯的组件和交互

不要先写一段文字解释用户应该如何理解页面。

### 2. 不用说明弥补设计问题

当页面难以理解时，按以下顺序处理：

1. 调整信息层级；
2. 修改标题和按钮名称；
3. 调整布局和组件；
4. 删除无关内容；
5. 最后才考虑增加一句必要说明。

不要通过增加副标题、提示卡片、操作步骤、Tooltip 和帮助文案，掩盖不清楚的交互。

### 3. 不因页面空而增加内容

留白不是功能缺失。

不要为了让页面显得丰富而添加：

* 欢迎语
* 装饰性统计卡片
* 无行动价值的状态
* “工作原理”区域
* 重复说明标题的副标题
* 最近活动
* 系统健康状态
* 不必要的操作指南
* 与当前任务无关的技术信息

### 4. 默认采用渐进披露

只默认展示当前任务所需的信息。

低频、高级或异常信息应根据需要放入：

* 展开区域
* 高级设置
* 详情页
* 帮助文档
* 错误详情
* 管理员或调试界面

不要一次性向普通用户展示系统的全部能力和内部状态。

### 5. 错误信息使用用户语言

错误提示应说明：

* 发生了什么；
* 用户现在可以做什么。

不要直接展示技术异常和内部实现。

示例：

不推荐：

> MongoDB configurationDocument 持久化失败。

推荐：

> 保存失败，请重试。

必要的错误代码和诊断信息应记录到日志或放入可展开的技术详情。

## 执行流程

在添加任何 UI 元素前，先回答：

1. 用户进入这个页面要完成什么任务？
2. 页面最主要的操作是什么？
3. 这个元素帮助用户采取什么行动？
4. 不展示这个元素是否会影响任务完成？
5. 这个信息来自用户需求，还是来自开发实现？
6. 它应该默认展示，还是按需展开？

无法明确回答第 1、3 项的元素，默认不添加。

第 4 项答案为“不会”的内容，默认删除或隐藏。

第 5 项答案为“开发实现”的内容，默认禁止进入 UI。

## 完成后的减法审查

实现完成后，必须进行一次 UI 减法审查：

* 删除无法支持主要任务的卡片和区域；
* 删除重复表达相同内容的标题和说明；
* 删除用户无法据此采取行动的状态；
* 删除所有不必要的内部实现细节；
* 将低频信息移入渐进披露区域；
* 检查是否通过文字解释掩盖了交互问题；
* 检查是否因为页面留白而添加了无关内容；
* 确保页面只有一个清晰的主要操作；
* 确保用户不需要阅读开发文档式说明才能使用页面。

## 最终判断标准

一个合格的 UI 应当做到：

* 用户可以凭借常见 UI 习惯完成主要任务；
* 页面不要求用户理解系统内部实现；
* 页面展示的是用户任务，而不是后端结构；
* 每一段文字都具有明确的行动价值；
* 删除任意非必要内容后，页面不会变得更难使用；
* UI 看起来像产品，而不是代码注释的可视化版本。
